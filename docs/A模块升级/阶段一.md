模块 A 歌词链路升级需求

## 阶段一

### 1. 目标

在模块 A 中新增“优先读取音频元数据 -> 直查同步歌词 LRC -> 必要时再走音乐指纹识别补充”的歌词主链。
当主链成功获取到可用的同步歌词时，优先使用该链路产出的歌词时间戳结果，替代当前直接使用 FunASR 作为歌词主结果的方案。

### 2. 方案决策

1. 元数据优先策略采用：
- 优先读取音频文件自带的 artist/title 元数据
- 当元数据完整且可用时，先直接查询 LRCLIB

2. 指纹识别补充链采用：
- AcoustID + Chromaprint

3. 同步歌词主链采用：
- LRCLIB

4. 歌词兜底方案采用：
- 保留 FunASR 作为兜底链路

5. 查询条件采用严格匹配：
- artist + title + duration

说明：
- 当前阶段不采用“宽松匹配优先”的策略。
- 这样做的目标是尽量降低拉取到错误版本歌词或错误时间轴的概率，尽可能减小 LRC 时间轴误差。
- 当前阶段不做复杂元数据清洗、别名归一化或多轮候选比对。

### 3. 主链执行要求

模块 A 的歌词获取主链调整为：

1. 先读取输入音频自带元数据。
2. 当元数据中存在可用的 artist + title 时，优先使用 artist + title + duration 直接查询 LRCLIB。
3. 当元数据缺失、不完整，或元数据直查未返回可用同步歌词时，再对输入音频执行音乐指纹识别。
4. 通过 AcoustID 获取歌曲识别结果。
5. 使用识别得到的 artist + title + duration 再次查询 LRCLIB。
6. 当 LRCLIB 返回同步歌词（带时间戳的 LRC）时，优先使用该结果进入当前歌词主链。
7. 当前阶段默认直接使用 LRCLIB 返回的同步歌词时间戳，不将 beat 吸附作为主链必选步骤。
8. 只有当元数据直查和指纹补充链均未返回可用同步歌词时，才进入 FunASR 兜底流。

### 4. 时间戳处理策略

当前阶段默认直接使用 LRCLIB 返回的同步歌词时间戳作为歌词主链结果。

这样定义的原因是：

- 根据已有经验，大多数歌词时间戳本身已经足够准确；
- 当前阶段优先完成“元数据直查 + 指纹补充 + 同步歌词主链 + FunASR 兜底”的主流程落地；
- 不应在第一阶段就把 beat 吸附作为强制门槛，以免扩大实现复杂度并引入额外误差。

当前阶段约束：

- 允许将 LRCLIB 返回的同步歌词时间戳直接作为当前主链输出；
- 不要求在当前版本中强制执行 snap to nearest beat；
- 只要 LRCLIB 返回的是可用同步歌词，就可以作为当前下游 Seg 切分的时间基准之一。

### 5. 主链与兜底链的判定规则

1. 当 LRCLIB 返回可用同步歌词时：
- 使用 LRC 主链结果；
- 替代当前 FunASR 直接产出的歌词主结果。

2. 当元数据直查未命中可用同步歌词时：
- 若音频元数据缺失、字段不完整，或 LRCLIB 未返回可用同步歌词，则继续走指纹补充链；
- 不将元数据直查失败直接视为主链最终失败。

3. 当 LRCLIB 仅返回纯文本歌词、没有同步时间戳时：
- 不使用该结果进入当前主链；
- 若当前仍未执行指纹补充链，则继续走指纹补充链；
- 若指纹补充链也未返回可用同步歌词，再走 FunASR 兜底流。

4. 当 LRCLIB 明确返回 `instrumental=true` 时：
- 直接视为“主链无可用歌词”；
- 不再进入 FunASR 兜底；
- 最终输出空 `lyric_sentence_units`；
- 同时记录 `provider=lrclib`、`reason=instrumental` 或等价原因字段。

5. 当 AcoustID 识别失败、歌曲匹配失败、LRCLIB 查询失败，或 LRC 内容不可用时：
- 统一走 FunASR 兜底流。

### 6. 实现边界说明

- 本阶段升级的重点是“新增元数据优先 + 指纹补充的 LRC 主链，并在当前阶段直接使用可用同步歌词进入下游”；
- FunASR 当前仍保留，职责调整为兜底链；
- 如果主链失败，不应阻塞模块 A 继续完成，应回退到现有 FunASR 兜底能力。

### 7. 接口契约与字段流转

本节只描述阶段一必需的字段契约，目标是明确每一个字段如何从外部服务进入模块 A，再如何进入现有 `ModuleAOutput`。

说明：

- 阶段一不修改 `ModuleAOutput` 最终契约；
- 阶段一新增的主要是“主链内部中间结构”和“来源判定字段”；
- 下游模块 B/C/D 继续只消费现有 `module_a_output.json`，不直接读取 AcoustID 或 LRCLIB 原始返回。

#### 7.1 字段流转总览

阶段一字段流转顺序如下：

1. 输入音频 `audio_path`
2. 音频元数据读取结果
3. 元数据直查 LRCLIB 结果
4. 必要时的音乐指纹识别结果
5. 必要时的 AcoustID 查询结果
6. 最终采用的 LRCLIB 查询结果
7. 内部标准化 `lyric_sentence_units`
8. `clean_lyric_units()` 清洗结果
9. `attach_lyrics_to_segments()` 挂载结果
10. 输出到 `ModuleAOutput.lyric_units`

其中：

- `big_segments` 与 `beats` 仍然来自现有 allin1 链路；
- `segments` 与 `energy_features` 仍然来自现有算法层；
- 本次升级只替换“歌词来源”，不改动现有节拍和分段主链。

#### 7.2 外部输入与元数据读取契约

主链输入只使用现有模块 A 已有输入，不新增用户侧必填参数。

```json
{
  "task_id": "string",
  "audio_path": "string",
  "duration_seconds": 123.45
}
```

字段说明：

- `task_id`
  - 来源：现有 `RuntimeContext.task_id`
  - 去向：最终继续写入 `ModuleAOutput.task_id`

- `audio_path`
  - 来源：现有 `RuntimeContext.audio_path`
  - 去向：
    - 传给音频元数据读取链路
    - 传给指纹识别链路
    - 传给 FunASR 兜底链路
    - 最终继续写入 `ModuleAOutput.audio_path`

- `duration_seconds`
  - 来源：现有 `probe_audio_duration()` 结果
  - 去向：
    - 作为元数据直查、AcoustID、LRCLIB 严格匹配辅助字段
    - 不单独写入 `ModuleAOutput`

阶段一建议在主链入口新增“音频元数据标准化结果”结构，供 LRCLIB 元数据直查使用。

```json
{
  "status": "ok|missing|failed",
  "artist": "string",
  "title": "string",
  "album": "string",
  "duration_seconds": 123.45,
  "source": "embedded_tags",
  "error": "string"
}
```

字段流转：

- `status`
  - 来源：音频标签读取结果判定
  - 去向：决定是否尝试元数据直查，或直接进入指纹补充链

- `artist`
  - 来源：音频文件自带 artist 标签
  - 去向：作为 LRCLIB 元数据直查条件的一部分

- `title`
  - 来源：音频文件自带 title 标签
  - 去向：作为 LRCLIB 元数据直查条件的一部分

- `album`
  - 来源：音频文件自带 album 标签
  - 去向：当前阶段仅用于日志和调试，不作为查询主键

- `duration_seconds`
  - 来源：本地探测音频时长
  - 去向：作为 LRCLIB 严格匹配辅助字段

- `source`
  - 来源：固定值 `embedded_tags`
  - 去向：仅用于日志和调试产物

- `error`
  - 来源：元数据读取异常或失败原因
  - 去向：仅用于日志和调试产物，不进入最终 `ModuleAOutput`

#### 7.3 指纹识别内部标准化契约

阶段一建议在模块 A 感知层内部新增“指纹识别标准化结果”结构，供后续 AcoustID 查询使用。

```json
{
  "fingerprint": "string",
  "duration_seconds": 123.45,
  "fingerprint_engine": "chromaprint",
  "status": "ok|failed",
  "error": "string"
}
```

字段流转：

- `fingerprint`
  - 来源：Chromaprint/fpcalc 生成结果
  - 去向：传给 AcoustID 查询

- `duration_seconds`
  - 来源：指纹工具输出或模块 A 已探测时长
  - 去向：传给 AcoustID 查询，并参与后续 LRCLIB 严格匹配

- `fingerprint_engine`
  - 来源：固定值 `chromaprint`
  - 去向：仅用于内部日志和调试产物

- `status`
  - 来源：指纹步骤执行结果
  - 去向：驱动“继续主链”或“回退 FunASR”

- `error`
  - 来源：异常信息或失败原因
  - 去向：仅用于日志和调试产物，不进入最终 `ModuleAOutput`

#### 7.4 AcoustID 查询标准化契约

阶段一建议不要把 AcoustID 原始响应直接向下游透传，而是在模块 A 内部先归一化为一个最小可用结构。

```json
{
  "status": "ok|no_match|failed",
  "artist": "string",
  "title": "string",
  "duration_seconds": 123.45,
  "score": 0.98,
  "acoustid_id": "string",
  "recording_id": "string",
  "raw_candidates": []
}
```

字段流转：

- `status`
  - 来源：AcoustID 查询结果判定
  - 去向：决定是否继续查询 LRCLIB，或直接回退 FunASR

- `artist`
  - 来源：AcoustID 命中的主艺人名
  - 去向：作为 LRCLIB 查询键的一部分

- `title`
  - 来源：AcoustID 命中的歌曲名
  - 去向：作为 LRCLIB 查询键的一部分

- `duration_seconds`
  - 来源：AcoustID 命中记录时长或本地音频时长
  - 去向：作为 LRCLIB 查询键的一部分

- `score`
  - 来源：AcoustID 匹配分数
  - 去向：仅用于内部筛选、日志与调试产物

- `acoustid_id`
  - 来源：AcoustID 结果主键
  - 去向：仅用于调试追踪

- `recording_id`
  - 来源：MusicBrainz recording id 或等价标识
  - 去向：仅用于调试追踪

- `raw_candidates`
  - 来源：AcoustID 候选列表
  - 去向：仅用于调试产物，不传给下游模块

#### 7.5 LRCLIB 查询标准化契约

阶段一建议将 LRCLIB 返回统一规范成以下内部结构，避免后续代码直接依赖外部 API 字段名。

```json
{
  "status": "synced|plain|not_found|failed",
  "artist": "string",
  "title": "string",
  "duration_seconds": 123.45,
  "plain_lyrics": "string",
  "synced_lyrics": "string",
  "provider": "lrclib",
  "provider_id": "string",
  "error": "string"
}
```

字段流转：

- `status`
  - 来源：LRCLIB 返回结果类型判定
  - 去向：
    - `synced`：进入 LRC 主链解析
    - `plain`：当前阶段直接回退 FunASR
    - `not_found|failed`：当前阶段直接回退 FunASR

- `artist`
  - 来源：LRCLIB 命中结果
  - 去向：用于内部校验和日志

- `title`
  - 来源：LRCLIB 命中结果
  - 去向：用于内部校验和日志

- `duration_seconds`
  - 来源：LRCLIB 命中结果或查询输入回填
  - 去向：用于内部校验和日志

- `plain_lyrics`
  - 来源：LRCLIB 纯文本歌词
  - 去向：阶段一不进入下游，仅保留调试值

- `synced_lyrics`
  - 来源：LRCLIB 同步歌词原文
  - 去向：传给 LRC 解析器，构造 `lyric_sentence_units`

- `provider`
  - 来源：固定值 `lrclib`
  - 去向：仅用于调试与来源记录

- `provider_id`
  - 来源：LRCLIB 记录主键或等价标识
  - 去向：仅用于调试追踪

- `error`
  - 来源：异常信息或失败原因
  - 去向：仅用于日志和调试产物

补充说明：

- 阶段一中的 LRCLIB 查询可能来自两条入口：
  - 元数据直查入口；
  - 指纹补充链入口。
- 两条入口最终都必须标准化为同一个 LRCLIB 查询结果结构，不向下游暴露来源差异。

#### 7.6 主链内部歌词标准化契约

无论歌词来自 LRCLIB 主链还是 FunASR 兜底链，进入算法层前都必须统一成现有 `perception.lyric_sentence_units` 可接受的结构。

阶段一统一结构如下：

```json
[
  {
    "start_time": 12.34,
    "end_time": 15.67,
    "text": "歌词内容",
    "confidence": 0.95,
    "token_units": [],
    "source_sentence_index": 0,
    "source": "lrclib|funasr"
  }
]
```

字段流转：

- `start_time`
  - LRCLIB 主链来源：LRC 行起始时间
  - FunASR 兜底来源：FunASR 分句后的起始时间
  - 去向：
    - 传给 `clean_lyric_units()`
    - 最终可能进入 `ModuleAOutput.lyric_units[].start_time`

- `end_time`
  - LRCLIB 主链来源：由“下一行起始时间”或“音频尾/可接受收尾规则”推导
  - FunASR 兜底来源：FunASR 分句后的结束时间
  - 去向：
    - 传给 `clean_lyric_units()`
    - 最终可能进入 `ModuleAOutput.lyric_units[].end_time`

- `text`
  - LRCLIB 主链来源：LRC 行文本
  - FunASR 兜底来源：FunASR 分句文本
  - 去向：
    - 传给 `clean_lyric_units()`
    - 最终进入 `ModuleAOutput.lyric_units[].text`

- `confidence`
  - LRCLIB 主链来源：规则默认值，阶段一由内部约定生成
  - FunASR 兜底来源：FunASR 置信度
  - 去向：
    - 传给 `clean_lyric_units()`
    - 最终进入 `ModuleAOutput.lyric_units[].confidence`

- `token_units`
  - LRCLIB 主链来源：阶段一默认空数组
  - FunASR 兜底来源：FunASR token 时间戳
  - 去向：
    - 传给 `clean_lyric_units()`
    - 若存在则进入 `attach_lyrics_to_segments()`
    - 最终可进入 `ModuleAOutput.lyric_units[].token_units`

- `source_sentence_index`
  - LRCLIB 主链来源：LRC 解析后的顺序索引
  - FunASR 兜底来源：FunASR 分句顺序索引
  - 去向：
    - 作为调试和挂载追踪字段
    - 最终可进入 `ModuleAOutput.lyric_units[].source_sentence_index`

- `source`
  - 来源：内部来源标记，值为 `lrclib` 或 `funasr`
  - 去向：阶段一建议仅保留在中间产物中，不直接写入当前 `ModuleAOutput` 最终契约

#### 7.7 算法层输入输出衔接

阶段一不改变现有算法层的主职责，只改变 `perception.lyric_sentence_units` 的来源。

当前衔接关系如下：

```json
{
  "perception.big_segments_stage1": "来自 allin1",
  "perception.beats": "来自 allin1",
  "perception.lyric_sentence_units": "来自 lrclib 或 funasr",
  "perception.sentence_split_stats": "来自 lrclib 解析统计或 funasr 分句统计"
}
```

字段流转：

- `perception.big_segments_stage1`
  - 来源：allin1 宏观段落输出
  - 去向：进入 `run_algorithm_stage()`，参与大段和小段计算

- `perception.beats`
  - 来源：allin1 beat 结构化输出
  - 去向：
    - 进入 `run_algorithm_stage()`
    - 最终进入 `ModuleAOutput.beats`

- `perception.lyric_sentence_units`
  - 来源：
    - 主链成功时来自 LRCLIB 解析结果
    - 主链失败时来自 FunASR
  - 去向：
    - 进入 `clean_lyric_units()`
    - 再进入 `attach_lyrics_to_segments()`

- `perception.sentence_split_stats`
  - 来源：
    - LRCLIB 主链时由 LRC 解析阶段生成基础统计
    - FunASR 兜底时复用现有 `sentence_split_stats`
  - 去向：
    - 进入内容角色编排流程
    - 作为窗口与歌词清洗的辅助统计

#### 7.8 最终 ModuleAOutput 契约映射

阶段一最终仍然输出现有 `ModuleAOutput`，字段映射关系如下。

```json
{
  "task_id": "RuntimeContext.task_id",
  "audio_path": "RuntimeContext.audio_path",
  "big_segments": "analysis_bundle.big_segments",
  "segments": "analysis_bundle.segments",
  "beats": "analysis_bundle.beats",
  "lyric_units": "analysis_bundle.lyric_units",
  "energy_features": "analysis_bundle.energy_features",
  "alias_map": "build_module_a_v2_alias_map(...)"
}
```

其中歌词相关字段必须满足以下最小契约：

```json
[
  {
    "segment_id": "string",
    "start_time": 12.34,
    "end_time": 15.67,
    "text": "歌词内容",
    "confidence": 0.95,
    "token_units": [],
    "source_sentence_index": 0,
    "unit_transform": "original|split|merged"
  }
]
```

字段流转：

- `segment_id`
  - 来源：`attach_lyrics_to_segments()` 根据时间重叠挂载到最终 `segments`
  - 去向：进入 `ModuleAOutput.lyric_units[].segment_id`

- `start_time`
  - 来源：主链或兜底链标准化结果，经清洗与必要裁剪后保留
  - 去向：进入 `ModuleAOutput.lyric_units[].start_time`

- `end_time`
  - 来源：主链或兜底链标准化结果，经清洗与必要裁剪后保留
  - 去向：进入 `ModuleAOutput.lyric_units[].end_time`

- `text`
  - 来源：清洗后的歌词文本
  - 去向：进入 `ModuleAOutput.lyric_units[].text`

- `confidence`
  - 来源：主链规则值或 FunASR 置信度，经清洗后保留
  - 去向：进入 `ModuleAOutput.lyric_units[].confidence`

- `token_units`
  - 来源：
    - LRCLIB 主链：阶段一通常为空
    - FunASR 兜底：沿用现有 token 时间戳
  - 去向：如存在则进入 `ModuleAOutput.lyric_units[].token_units`

- `source_sentence_index`
  - 来源：标准化分句顺序
  - 去向：如保留则进入 `ModuleAOutput.lyric_units[].source_sentence_index`

- `unit_transform`
  - 来源：歌词切分/合并/原样保留时的内部标记
  - 去向：如保留则进入 `ModuleAOutput.lyric_units[].unit_transform`

#### 7.9 阶段一新增中间产物建议

为保证可追溯性，阶段一建议新增以下中间产物。它们只服务于调试和恢复，不改变最终 `ModuleAOutput` 契约。


### 8. 分段实施设计草案

本节用于指导阶段一的实际落地顺序，目标是在不破坏现有模块 A 主链的前提下，以最小改动完成“LRCLIB 主链优先，FunASR 兜底”的歌词链路升级。

总体设计原则如下：

- 不重写模块 A，只在现有歌词来源前增加轻量编排层；
- 不平台化，不在阶段一引入 provider registry、复杂策略工厂或通用工作流引擎；
- 不修改 `ModuleAOutput` 最终契约，只替换 `perception.lyric_sentence_units` 的来源；
- 不让外部服务字段直接进入算法层，所有外部结果必须先标准化；
- 主链失败不等于模块 A 失败，必须稳定回退到 FunASR。

#### 8.1 分段目标与推荐顺序

建议按以下五段推进，每一段都可独立验收。

##### 第一段：先建立歌词来源编排骨架

目标：

- 把当前“直接调用 FunASR 产出歌词”的单链路流程，调整为“主链尝试 -> 失败回退”的双链路骨架；
- 暂时允许主链函数为空实现或始终返回失败，只要整体流程可继续回退到 FunASR 即可。

本段只解决两个问题：

1. 模块 A 从哪里拿歌词；
2. 当主链失败时如何回退。

推荐落点：

- 新增统一入口，例如 `resolve_lyrics_for_module_a(...)`；
- 返回统一歌词结果，而不是把 LRCLIB/FunASR 差异暴露给下游；
- 在本段完成后，即使 LRCLIB 还未接入，模块 A 仍可维持现有能力。

##### 第二段：接入元数据直查能力

目标：

- 完成音频文件元数据读取；
- 判断元数据是否满足最小可用条件；
- 当元数据可用时，优先用 `artist + title + duration` 直接查询 LRCLIB。

本段边界：

- 只做轻量元数据读取；
- 不做复杂文本清洗；
- 不做别名归一化；
- 不做多轮候选比对；
- 元数据直查失败不视为异常，只进入下一段的指纹补充链。

推荐判定：

- `artist` 与 `title` 均非空：允许执行元数据直查；
- 任一关键字段缺失：直接进入指纹补充链；
- 元数据直查命中同步歌词：主链成功；
- 元数据直查未命中可用同步歌词：进入指纹补充链。

##### 第三段：接入指纹识别与 AcoustID

目标：

- 完成音频指纹生成；
- 完成 AcoustID 查询；
- 产出可供 LRCLIB 查询使用的 `artist/title/duration`。

本段边界：

- 只负责“识别歌曲”；
- 不负责歌词是否可用的最终判定；
- 不做宽松匹配；
- 不做复杂候选排序平台化；
- 不做并行多源识别。

推荐判定：

- 指纹生成失败：直接标记主链失败；
- AcoustID 无命中：直接标记主链失败；
- 命中但 `artist/title` 不完整：直接标记主链失败；
- 命中且关键信息完整：进入 LRCLIB 查询阶段。

##### 第四段：接入 LRCLIB 与 LRC 解析

目标：

- 支持元数据直查与指纹补充链两种入口查询 LRCLIB；
- 仅当返回同步歌词时进入主链；
- 将 LRC 解析成内部统一歌词句单元。

本段明确不做的事情：

- 不将 plain lyrics 送入当前主链；
- 不引入 beat 吸附；
- 不做文本纠偏；
- 不做多版本歌词比对。

推荐增加一个独立判定函数，例如：

- `is_synced_lyrics_usable(...)`

最小判定条件建议如下：

- 存在同步时间戳；
- 存在足够数量的有效歌词行；
- 时间戳单调递增；
- 歌词文本非空。

##### 第五段：统一主链与兜底链出口

目标：

- 把 LRCLIB 主链与 FunASR 兜底链统一收口；
- 统一输出标准化 `lyric_sentence_units`；
- 明确记录本次最终实际采用的 provider 与原因。

推荐输出结果至少包含：

- `lyric_sentence_units`
- `provider`
- `reason`
- `debug_artifact_paths`

这样下游算法层只认一件事：

- 当前任务已经得到可消费的歌词句单元，不关心其来自 LRCLIB 还是 FunASR。

##### 第六段：补齐可追溯性与测试

目标：

- 补齐调试产物；
- 补齐异常场景覆盖；
- 固化阶段一的验收标准。

推荐补齐内容：

- `fingerprint_result.json`
- `acoustid_match.json`
- `lrclib_match.json`
- `lyric_sentence_units.json`
- `selected_provider.json`

建议放在主功能跑通之后补齐，避免在主链尚未打通前就先做厚外围工程。

#### 8.2 最小代码结构建议

阶段一建议新增的是“歌词来源编排层”，而不是新的大模块。推荐只增加以下几类职责单元：

1. 元数据适配层
- 负责读取音频文件标签；
- 负责将元数据标准化；
- 负责为 LRCLIB 提供元数据直查输入。

2. 识别适配层
- 负责调用 Chromaprint/fpcalc；
- 负责调用 AcoustID；
- 负责将外部识别结果标准化。

3. 歌词适配层
- 负责调用 LRCLIB；
- 负责解析 LRC；
- 负责将同步歌词转换成统一句单元。

4. 歌词选择器
- 负责主链尝试；
- 负责失败回退；
- 负责输出最终 provider 决策。

5. 模块 A 接入点
- 只替换 `perception.lyric_sentence_units` 的来源；
- 不改动 `beats`、`segments`、`energy_features` 的生产逻辑。

如果要控制复杂度，阶段一不建议提前引入以下设计：

- provider 注册中心；
- 通用策略工厂；
- 通用状态机框架；
- 多 provider 并发竞争；
- 宽松匹配与评分系统；
- 面向未来扩展的抽象过度预埋。

#### 8.3 推荐目录与代码落点

在不重构现有模块 A 目录的前提下，建议新增以下最小落点。具体文件名可结合现有工程目录微调，但职责边界应保持一致。

```text
module_a/
  perception/
    model/
      lyrics_resolver.py        # 统一入口：主链尝试与兜底回退
      metadata_reader.py        # 音频元数据读取与标准化
      acoustid_client.py        # 指纹与 AcoustID 识别适配
      lrclib_client.py          # LRCLIB 查询适配
      lrc_parser.py             # LRC 解析与标准化
      lyric_types.py            # 阶段一内部最小标准化结构
```

若现有工程已存在更贴近的目录，应优先复用现有目录，避免只为这次升级新建一整套层级。

#### 8.4 推荐函数拆分

建议把职责收敛在少量清晰函数中，不要把控制流分散到多个调用点。

推荐最小函数集合如下：

1. `resolve_lyrics_for_module_a(runtime_context, perception_inputs)`
- 功能：模块 A 获取歌词的统一入口；
- 职责：先尝试元数据直查，再尝试指纹补充链，失败则回退 FunASR；
- 输出：统一标准化歌词结果与 provider 记录。

2. `read_embedded_metadata(audio_path, duration_seconds)`
- 功能：读取音频文件自带元数据并标准化；
- 职责：判断是否满足元数据直查最小条件。

3. `try_lrc_main_flow(audio_path, duration_seconds)`
- 功能：执行“元数据直查 -> 指纹补充 -> LRCLIB -> LRC 解析”的主链；
- 职责：仅负责主链，不负责 FunASR 回退；
- 输出：成功则返回标准化歌词句单元，失败则返回失败原因。

4. `build_fingerprint_result(audio_path)`
- 功能：生成指纹并标准化；
- 职责：封装 Chromaprint/fpcalc 调用与异常处理。

5. `query_acoustid_match(fingerprint_result)`
- 功能：查询 AcoustID；
- 职责：把候选结果归一化为内部最小结构。

6. `query_lrclib_lyrics(artist, title, duration_seconds)`
- 功能：查询 LRCLIB；
- 职责：只处理歌词服务返回，不承担主流程编排职责。

7. `parse_synced_lyrics_to_sentence_units(synced_lyrics, audio_duration)`
- 功能：把 LRC 文本解析成统一 `lyric_sentence_units`；
- 职责：补齐 `end_time`、索引、基础置信度等内部字段。

8. `try_funasr_fallback(audio_path, runtime_context)`
- 功能：执行现有 FunASR 兜底链；
- 职责：复用现有逻辑，并转换成统一标准化句单元。

#### 8.5 主流程伪代码

以下伪代码仅表达控制结构，不限制具体文件组织。

```python
def resolve_lyrics_for_module_a(runtime_context, perception_inputs):
    """
    功能说明：统一解析模块 A 歌词来源，优先尝试 LRCLIB 主链，失败时回退到 FunASR。
    参数说明：
    - runtime_context: 当前任务运行上下文，至少包含 task_id 与 audio_path。
    - perception_inputs: 感知层已有输入，至少包含音频时长等辅助信息。
    返回值：
    - dict: 包含 lyric_sentence_units、provider、reason、debug_artifact_paths 的结果。
    异常说明：
    - 不向上抛出主链失败异常，统一在内部转为回退决策。
    边界条件：
    - 当 LRCLIB 主链任一步失败时，必须保持 FunASR 可继续执行。
    """
    main_result = try_lrc_main_flow(
        audio_path=runtime_context.audio_path,
        duration_seconds=perception_inputs.duration_seconds,
    )
    if main_result.status == "success":
        return {
            "lyric_sentence_units": main_result.lyric_sentence_units,
            "provider": "lrclib",
            "reason": main_result.reason,
            "debug_artifact_paths": main_result.debug_artifact_paths,
        }

    fallback_result = try_funasr_fallback(
        audio_path=runtime_context.audio_path,
        runtime_context=runtime_context,
    )
    return {
        "lyric_sentence_units": fallback_result.lyric_sentence_units,
        "provider": "funasr",
        "reason": main_result.reason or "fallback",
        "debug_artifact_paths": main_result.debug_artifact_paths,
    }
```

1. `read_embedded_metadata(audio_path, duration_seconds, logger)`
- 功能：读取音频元数据；
- 输出：标准化元数据结构。

2. `query_lrclib_lyrics(artist, title, duration_seconds, logger)`
- 功能：以严格匹配条件查询 LRCLIB；
- 输出：标准化 LRCLIB 查询结果。

3. `parse_synced_lyrics_to_sentence_units(synced_lyrics, audio_duration, logger)`
- 功能：把同步歌词解析为统一句级歌词单元；
- 输出：`lyric_sentence_units`。

4. `build_fingerprint_result(audio_path, duration_seconds, logger)`
- 功能：生成音频指纹并标准化；
- 输出：标准化指纹结果。

5. `query_acoustid_match(fingerprint_result, logger)`
- 功能：查询 AcoustID 并归一化候选结果；
- 输出：标准化歌曲识别结果。

6. `resolve_lyrics_with_priority(...)`
- 功能：统一歌词来源入口；
- 职责：
  - 先尝试元数据直查；
  - 再尝试指纹补充链；
  - 最后回退 FunASR；
- 输出：
  - `lyric_sentence_units`
  - `sentence_split_stats`
  - `provider`
  - `reason`
  - `debug_artifact_paths`

##### 8.8.6 perception.py 中的最小改造方式

阶段一最重要的实现原则是：

- 保留 `PerceptionBundle` 最终字段结构；
- 保留当前并发结构；
- 只把“FunASR 直接作为歌词唯一来源”改成“统一歌词解析入口”。

推荐改法如下：

1. 保留当前：
- Demucs 分离；
- allin1 分析；
- Librosa 双轨提取；
- vocal RMS 预检；
- FunASR 实际执行函数。

2. 把当前“直接等待 FunASR future 并写 `lyric_sentence_units`”的那段逻辑，收敛为：
- 先准备好 FunASR fallback 执行能力；
- 再调用 `resolve_lyrics_with_priority(...)`；
- 最终由 resolver 返回统一的歌词句单元和来源信息。

3. `PerceptionBundle.lyric_sentence_units` 的含义保持不变：
- 仍然表示“当前任务最终实际采用的歌词句单元”；
- 只是不再默认等于 FunASR 产出。

##### 8.8.7 建议的统一返回结构

阶段一建议让 `resolve_lyrics_with_priority(...)` 返回如下最小结构：

```json
{
  "provider": "lrclib|funasr",
  "reason": "metadata_synced|fingerprint_synced|metadata_missing|plain_only|not_found|identify_failed|fallback",
  "lyric_sentence_units": [],
  "sentence_split_stats": {},
  "debug_artifact_paths": {}
}
```

这样可以保证：

- 感知层日志有解释性；
- 中间产物可追溯；
- 算法层仍然无感知。

##### 8.8.8 LRC 解析输出要求

阶段一的 `lrc_parser.py` 不需要做复杂处理，只要满足现有算法层可消费即可。

建议统一输出：

```json
[
  {
    "start_time": 12.34,
    "end_time": 15.67,
    "text": "歌词内容",
    "confidence": 0.95,
    "token_units": [],
    "source_sentence_index": 0,
    "unit_transform": "original"
  }
]
```

具体约束：

- `start_time` 来自 LRC 行时间；
- `end_time` 由下一行时间或音频尾推导；
- `confidence` 阶段一建议固定为较高规则值，例如 `0.95`；
- `token_units` 阶段一允许为空数组；
- `unit_transform` 阶段一默认使用 `original`。

##### 8.8.9 纯音乐与无歌词的处理规则

阶段一必须明确区分以下几类结果：

1. 有同步歌词
- 正常进入主链；
- 输出标准化 `lyric_sentence_units`。

2. 只有 plain lyrics
- 当前阶段不进入主链；
- 继续尝试指纹补充链或回退 FunASR。

3. 标记为 instrumental / 无歌词
- 不伪造“歌词文本”；
- 不生成假的 `lyric_sentence_units`；
- 若 LRCLIB 已明确返回 `instrumental=true`，则直接终止歌词主链；
- 不再进入 FunASR 兜底；
- 最终以空 `lyric_sentence_units` 进入后续算法层。

4. LRCLIB 有记录但歌词字段为空
- 与 instrumental 同等处理；
- 不把空记录包装成可用歌词。

原因是：

- 模块 A 的 `lyric_units` 是时间约束数据，不是播放器展示文案；
- 阶段一不应把“纯音乐占位文案”混入下游算法；
- 纯音乐样本更适合通过 `segments`、`beats`、`energy_features` 驱动后续分镜。

##### 8.8.10 推荐实施顺序

结合当前代码现实，最推荐的实施顺序如下：

1. 先做 `metadata_reader.py`
- 目标：验证样本音频是否带有可用 artist/title 元数据。

2. 再做 `lrclib_client.py + lrc_parser.py`
- 目标：先打通“元数据直查 -> 标准化歌词句单元”；
- 这一步可以在 Windows 环境独立验证。

3. 再做 `lyrics_resolver.py`
- 目标：先实现“元数据直查 -> FunASR fallback”的统一入口。

4. 最后补 `acoustid_client.py`
- 目标：把“元数据查不到 -> 指纹补充”完整接上。

这样拆的原因是：

- 能尽早验证真实收益；
- Windows 环境可先完成大部分新增功能验证；
- 不会被 allin1/natten 的 Linux 限制卡住整个阶段一开发。
