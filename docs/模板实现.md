# 模板实现设计

## 1. 文档目标

本文档用于确定“模板引擎”这一层的正式实现方向。

这里说的模板，不是泛指任何视频生成能力，而是当前已经明确的程序化短镜头模板，例如：

- `center`：单纯把视觉意象放在视频中间
- `grid`：从左到右或从右到左，依次跳出三个矩形（或后续扩展为其他形状）
- `scroll`：使用至少两张图或一条长卷轴素材连续滚动

本文档只讨论这层能力如何接入项目，不讨论 A/B/C 主流程重写，不讨论旧实验代码继续长期保留。

---

## 2. 当前结论

### 2.1 正式模板引擎改用 Remotion

模板引擎的正式落地方向确定为 `Remotion`。

原因不是为了追求“换技术栈”，而是因为当前模板层真正缺的是：

- 节奏感
- 可视化预览
- 高效调参
- 组件化复用
- 更自然的动画表达

这些点，Remotion 明显比当前的 Python 帧拼接实验代码更适合。

### 2.2 现有 Python `template_engine/` 只作为过渡验证代码

当前仓库里已经临时写出的 Python `template_engine/`，只承担过渡验证作用。

一旦 Remotion 模板链路跑通，这部分代码要整体删除：

- 删除目录
- 删除脚本
- 删除注释
- 删除日志
- 删除文档中的旧实现描述

不保留兼容层，不做双维护。

### 2.3 不再把 Remotion 或 ComfyUI 写成“生成模式”

`remotion_template` 不是生成模式，`comfyui` 也不该是生成模式。

它们都是当前系统内唯一确定的正式实现策略：

- 模板渲染层使用 Remotion
- 模块 C 图像生成层使用 ComfyUI

过去配置和代码里出现的 `render_backend`、`mode`、`多策略选择` 等说法，是早期架构遗留。

后续需要逐步清理，不应在新设计中继续放大这类“伪可选项”。

### 2.4 单独运行与全链路运行共用同一套正式链路

Remotion 这层不分“实验模式”和“正式模式”。

正确做法是：

- 从一开始就按正式链路设计
- 但这套正式链路天然支持“拆出来单独运行”

也就是说：

- 任务重做
- 单 shot 重做
- 完整 D 模块调用

都应该共用同一套 request schema 和同一套渲染执行器。

这比先做一套 demo 入口、以后再接主链路更统一，也更符合本项目“不同粒度产物可重做”的整体设计。

## 3. 设计原则

### 3.1 模板只负责几何布局与时间运动

模板层负责的是：

- 视觉意象如何摆放
- 何时进入
- 如何移动
- 如何停顿
- 如何按节奏变化

模板层不负责：

- 主观背景审美
- 自作主张加边框、卡片、线框
- 额外决定素材风格

### 3.2 背景由调用方明确传入

模板不默认指定背景颜色，不主动决定背景图，不主动加边框语言。

背景由调用方明确传入，例如：

- 底图
- 底视频
- 纯色层
- 空白层

模板组件只消费这个背景定义。

### 3.3 模板组件不认识素材目录结构

模板只接受明确的素材字段，不负责自己去猜：

- 哪个目录是 frames
- 哪个文件是 start/end
- 哪些图该拼成 scroll

这些素材整理工作由 Python 侧调用方完成，再传给 Remotion。

### 3.4 `scroll` 运动方式不写死

`scroll` 并不强制只能做 stop-and-go。

当前至少应支持两类滚动方式：

- `linear`
- `step_hold`

哪种更合适，取决于调用方提供的视觉素材。

如果素材本身适合长卷展开，匀速滚动也完全成立。

## 4. 推荐目录结构

正式模板工程建议独立放在仓库根目录，不散进 Python 包内部。

```text
music_video_pipeline/
├─ remotion_templates/
│  ├─ package.json
│  ├─ tsconfig.json
│  ├─ remotion.config.ts
│  ├─ src/
│  │  ├─ Root.tsx
│  │  ├─ types.ts
│  │  ├─ compositions/
│  │  │  ├─ CenterTemplate.tsx
│  │  │  ├─ GridTemplate.tsx
│  │  │  └─ ScrollTemplate.tsx
│  │  ├─ shared/
│  │  │  ├─ BackgroundLayer.tsx
│  │  │  ├─ SymbolLayer.tsx
│  │  │  ├─ easing.ts
│  │  │  ├─ beat.ts
│  │  │  └─ layout.ts
│  │  └─ fixtures/
│  │     ├─ center.json
│  │     ├─ grid.json
│  │     └─ scroll.json
├─ src/music_video_pipeline/
├─ scripts/
├─ configs/
└─ runs/
```

### 4.1 为什么不用 `demo/`

这里不使用 `demo/` 命名。

原因很简单：

- 这套工程不是临时 demo
- 它从一开始就是正式模板引擎
- 以后不希望因为目录名不准确再做无意义重命名

所以这里使用 `fixtures/`：

- 语义中性
- 既能做样例输入
- 也能做本地预览与测试输入

### 4.2 各目录职责

`Root.tsx`

- 注册全部 Composition

`types.ts`

- 定义模板请求 JSON 对应的 TypeScript 类型

`compositions/`

- 一个模板一个文件

`shared/`

- 背景层、节拍工具、缓动工具、布局辅助

`fixtures/`

- 本地预览和快速验证使用的样例 props 文件

## 5. 模板请求契约

### 5.1 总体原则

Python 侧不直接给 Remotion 传“零碎参数”，而是写出一个正式的模板请求 JSON。

这个 JSON 同时服务于：

- 单独运行
- 任务重做
- D 模块正式调用

所以它不是 demo 结构，而是正式契约。

### 5.2 基础结构

建议统一为：

```json
{
  "template": "center",
  "width": 1280,
  "height": 720,
  "fps": 24,
  "duration_in_frames": 48,
  "bpm": 130,
  "background": {
    "kind": "image",
    "src": "M:/path/to/bg.png"
  },
  "layout": {},
  "motion": {}
}
```

### 5.3 背景定义

建议统一如下：

```json
{
  "background": {
    "kind": "none"
  }
}
```

或：

```json
{
  "background": {
    "kind": "solid",
    "color": "#FFFFFF"
  }
}
```

或：

```json
{
  "background": {
    "kind": "image",
    "src": "M:/path/to/bg.png"
  }
}
```

或：

```json
{
  "background": {
    "kind": "video",
    "src": "M:/path/to/bg.mp4"
  }
}
```

注意：

- 背景是什么，由调用方决定
- 模板不擅自补背景风格

## 6. 三个模板的正式组件设计

### 6.1 `CenterTemplate`

#### 语义

- 单个视觉意象置于画面中心
- 背景由调用方传入
- 模板不补边框、不补卡片、不补线框

#### 请求示例

```json
{
  "template": "center",
  "width": 1280,
  "height": 720,
  "fps": 24,
  "duration_in_frames": 48,
  "bpm": 130,
  "background": {
    "kind": "none"
  },
  "symbol": {
    "src": "M:/path/to/symbol.png"
  },
  "layout": {
    "scale": 0.42
  },
  "motion": {
    "beat_scale": 1.04
  }
}
```

#### 组件责任

- 读取背景层
- 把单图摆在中心
- 可选按 BPM 做轻微节拍缩放

这里的 `beat_scale` 只表达运动，不表达审美。

### 6.2 `GridTemplate`

#### 语义

- 三个矩形或后续扩展形状
- 从左到右或从右到左依次跳出
- 一个格子对应一个贴图/视觉符号

#### 请求示例

```json
{
  "template": "grid",
  "width": 1280,
  "height": 720,
  "fps": 24,
  "duration_in_frames": 48,
  "bpm": 130,
  "background": {
    "kind": "video",
    "src": "M:/path/to/bg.mp4"
  },
  "symbols": [
    {"src": "M:/path/to/a.png"},
    {"src": "M:/path/to/b.png"},
    {"src": "M:/path/to/c.png"}
  ],
  "layout": {
    "direction": "left_to_right",
    "gap": 24,
    "top_ratio": 0.2,
    "height_ratio": 0.55
  },
  "motion": {
    "stagger_frames": 4,
    "enter_frames": 8,
    "overshoot": 0.12
  }
}
```

#### 组件责任

- 绘制背景层
- 布局三个槽位
- 依次做进入动画
- 支持 overshoot / stagger

模板本身不去决定矩形边框审美，只决定布局和时间关系。

### 6.3 `ScrollTemplate`

#### 语义

- 至少两张图或一条长卷轴素材
- 连续滚动
- 可匀速，也可分段滑动停顿

#### 请求示例

```json
{
  "template": "scroll",
  "width": 1280,
  "height": 720,
  "fps": 24,
  "duration_in_frames": 72,
  "bpm": 130,
  "background": {
    "kind": "none"
  },
  "symbols": [
    {"src": "M:/path/to/scroll_1.png"},
    {"src": "M:/path/to/scroll_2.png"}
  ],
  "layout": {
    "direction": "left_to_right",
    "panel_width_ratio": 1.0
  },
  "motion": {
    "motion_type": "linear"
  }
}
```

或：

```json
{
  "motion": {
    "motion_type": "step_hold",
    "step_frames": 6,
    "hold_frames": 18
  }
}
```

#### 组件责任

- 生成连续 strip
- 根据 `motion_type` 渲染滚动方式
- 不自行补额外边框和风格装饰

## 7. `Root.tsx` 的组织方式

`Root.tsx` 只做 Composition 注册，不写死单个模板逻辑。

建议结构：

```tsx
<Composition id="CenterTemplate" component={CenterTemplate} ... />
<Composition id="GridTemplate" component={GridTemplate} ... />
<Composition id="ScrollTemplate" component={ScrollTemplate} ... />
```

这样 Python 侧只需要决定：

- 使用哪个模板
- 传哪份 props JSON

而不需要关心 React 组件内部细节。

## 8. Python 如何喂 JSON 给 Remotion

### 8.1 Python 侧职责

Python 侧负责：

1. 整理素材路径
2. 组装模板请求 JSON
3. 把 JSON 写入 `runs/...`
4. 调 Remotion CLI 渲染

Python 不负责：

- 模板动画细节
- 模板组件内部布局

### 8.2 建议输出位置

正式链路调用时，建议放到对应任务目录内，例如：

```text
runs/<task_id>/artifacts/template_requests/
    shot_001.center.json
    shot_002.grid.json
    shot_003.scroll.json
```

任务重做或链路外单独运行时，也复用同样的契约和同样的输出组织规则。

### 8.3 调用命令建议

在 `remotion_templates/` 目录中执行：

```powershell
npx remotion render GridTemplate M:\...\segment_001.mp4 --props=M:\...\shot_002.grid.json
```

或由 Python 通过 `subprocess.run()` 调用。

### 8.4 Python 侧建议函数

建议在 Python 侧收口为一个正式调用器，例如：

```python
def render_template_segment(
    project_dir: Path,
    composition_id: str,
    props_json_path: Path,
    output_path: Path,
) -> None:
    ...
```

注意这里不是“demo 渲染器”，而是正式模板片段渲染执行器。

## 9. 与任务重做机制的统一关系

这是本设计里最关键的一点。

### 9.1 不单独设计“实验模式”

本项目已经有“不同粒度产物可重做”的设计。

所以 Remotion 这一层不应再额外设计：

- demo 模式
- standalone 模式
- 实验渲染模式

这些说法都会把同一能力拆成多套入口。

### 9.2 正确做法

只保留一套正式能力：

- 模板请求 JSON
- 模板渲染执行器
- 模板输出产物

调用来源可以不同，但执行器只有一个。

### 9.3 两种调用来源

#### 来源一：任务重做

当系统已经存在：

- C 的素材
- 任务状态
- 已有部分中间产物

就由“任务重做入口”重新生成对应 template request，再调用同一个 Remotion 渲染器。

#### 来源二：完整链路

当 B/C/D 正常执行时，由 D 模块把当前 shot 转成 template request，再调用同一个 Remotion 渲染器。

这两种场景共用一套 request schema 和一套执行器。

这比先做一套独立实验入口、以后再接主链路更统一。

## 10. 与 D 模块的关系

### 10.1 D 模块不是“选择多个生成模式”

这里要明确纠偏：

- D 模块里不应该继续扩大“render_backend / mode”这种历史遗留概念
- Remotion 不是一个“用户自由切换的生成模式”

更准确的说法应该是：

- D 模块拥有正式的模板渲染能力
- 这项能力由 Remotion 实现
- ToonCrafter / 帧插值链路并列保留，但不是通过一套泛化的“多后端模式选择”去包装

### 10.2 D 模块真正新增的能力

D 模块后续需要新增的是：

1. `shot -> template request` 的转换
2. 调用 Remotion 渲染器产出 `segment_xxx.mp4`
3. 将结果纳入现有状态与产物目录

### 10.3 统一输出

无论来自任务重做还是完整链路，模板片段输出都应保持与 D 模块现有片段规则一致，例如：

```text
runs/<task_id>/segments/segment_001.mp4
```

这样后面的拼接逻辑不需要额外分叉。

## 11. 实施顺序

### 11.1 当前阶段

1. 新建 `remotion_templates/`
2. 初始化正式 Remotion 工程
3. 先实现 `CenterTemplate`
4. 再实现 `GridTemplate`
5. 再实现 `ScrollTemplate`
6. 用 `fixtures/` 与 `runs/.../template_requests/` 跑通 JSON -> mp4

### 11.2 过渡阶段

1. 用已有 `runs/.../artifacts/frames` 和其他中间图，生成正式 template request
2. 从 Python 调 Remotion CLI
3. 确认任务重做场景可用

### 11.3 正式接入阶段

1. 在 D 模块中加入 `shot -> template request` 转换
2. 调用正式模板渲染执行器
3. 接入现有状态与片段目录
4. 完成后删除 Python `template_engine/`

---

## 12. 当前决定

本轮已经确定以下几点：

1. 模板引擎正式改用 Remotion。
2. Python `template_engine/` 是过渡验证代码，后续整体删干净。
3. `demo/` 不作为正式目录名，改用 `fixtures/`。
4. 模板只负责几何布局与时间运动，不负责底层审美。
5. 背景由调用方明确传入。
6. `scroll` 不写死为 stop-and-go，至少支持 `linear` 与 `step_hold`。
7. Remotion 不单独作为“生成模式”概念存在。
8. 单独运行与全链路运行共用同一套正式 request schema 和渲染执行器。

这就是后续开工的正式设计基线。
